# Satsang Portal — PRD & Spec (v0.3)

Nov 2, 2026

## Status and working assumptions

Draft v0.3 (ready for build), updated with decisions made on Oct 26 and Nov 2, 2026. Technical design: [design.md](design.md). All open questions are resolved (see the end of this document).

- **Decided:** bhaktas never log in. They see the schedule, submit availability while voting is open, and view and download the allocation. They cannot edit it.
- **Decided:** one shared admin account, username + password, stored hashed.
- **Decided:** bhaktas are identified by name only, matched against the master list. No phone, email or other personal data is collected or stored.
- **Decided:** fixed weekly cadence — satsang every Saturday 7:00 pm IST; voting opens Monday morning, closes Tuesday end of day; allocation published Wednesday morning. v1 runs this with admin clicks; v2 runs it fully on a schedule.
- **Decided:** allocation is generated by the system from an admin-chosen slokam template; the admin can adjust it before or after publishing.

## Hypothesis

We believe replacing the weekly WhatsApp poll and hand-built slokam list with a portal that opens voting, closes it and publishes the allocation on a fixed schedule will remove the need for anyone to start the poll or build the list, with every available master-list bhakta seeing their slokams by Wednesday morning IST.

## Problem

**Who:** The batch coordinator (admin) who runs a weekly satsang and assigns slokams to each bhakta, and the bhaktas in that batch.

**Today:** Someone posts a poll in the batch's WhatsApp group each week. Only group members can vote, which keeps it to the batch. The admin then reads the results and assigns slokams by hand from the master spreadsheet.

**Pain points:**

- Every week a person has to remember to start the poll and to build the allocation list.
- Late cancellations leave slokams uncovered with no agreed backup.
- Re-splitting slokams by hand (4 per person one week, 8 the next) is slow and error-prone.
- Moving off WhatsApp loses its built-in membership check, so the portal must enforce the master list itself.

## Personas and use cases

| Persona | Access | Core jobs |
| --- | --- | --- |
| Admin (coordinator) | One shared username + password | Maintain the master list of names; set the weekly schedule; upload and choose a slokam template (e.g. 4 or 8 per bhakta); review, adjust and publish the allocation (v1) or let the schedule do it (v2) |
| Bhakta (participant) | No login, public link | See when the next satsang is and whether voting is open; submit availability by name; view and download the published allocation (read-only) |

**Bhakta availability options:**

1. Available
2. Not available
3. Available, and willing to be a backup for someone who drops out

## Non-goals (v1)

- No bhakta accounts, passwords or OTP login. Identity is the bhakta's name, matched to the master list.
- No phone numbers, emails or other personal details for bhaktas — not collected, not stored.
- No bhakta editing of the allocation. Bhaktas can only view and download.
- No payments, donations or attendance tracking on the day.
- No video/streaming or chanting audio. The portal only schedules and allocates.
- No WhatsApp/SMS messaging. The portal link is shared in the WhatsApp group once and reused weekly.
- No multiple admin accounts or roles. One shared admin login.
- No editing of slokam text inside the portal. Templates are maintained as spreadsheets and uploaded.

## Solution overview and weekly lifecycle

Every week runs the same cycle for the Saturday 7:00 pm IST satsang. In v1 the admin clicks to open voting, close it, generate and publish; in v2 a scheduler does all four on its own, and the admin only steps in to fix exceptions.

**Lifecycle (6 states):** Draft → Registration open (bhaktas vote) → Registration closed → Allocation drafted (template chosen, generated, edited) → Published (bhaktas view and download) → Satsang held.

| Step | When (IST) | v1 (MVP) | v2 (automated) |
| --- | --- | --- | --- |
| Next satsang created | After the previous satsang ends | Admin creates it | Auto-created from the weekly schedule |
| Voting opens | Monday 6:00 am | Admin clicks Open | Scheduler opens it |
| Voting closes | Tuesday 11:59 pm | Admin clicks Close | Scheduler closes it |
| Allocation generated | Right after close | Admin selects template, clicks Generate | Scheduler generates it |
| Allocation published | Wednesday 6:00 am | Admin reviews and clicks Publish | Auto-published at that time; admin may edit before or after |
| Satsang | Saturday 7:00 pm | — | — |

Bhaktas only ever touch two stages: voting while open, and viewing the published allocation.

## Allocation logic spec

The system fills the chosen template's rows with this week's chanters, top to bottom, then names backups. The template's rows are the blocks: each row already says which slokams it covers, so blocks can differ in size (2, 3, 4 or 5 slokams). Output is deterministic: regenerating with the same inputs gives the same grid. **Rules below confirmed Oct 26.**

**Template format (upload):** columns A–E of the batch's existing allocation sheet are the template Two A2322 templates so far, both from the "Satsang Chart" sheet: A2322-Allocation.xlsx (short blocks of 3–4 slokams, 53 to fill) and satsang 12 allocation list.xlsx (long blocks of 6–7 slokams, 28 to fill). In the long-block sheet one "Allocated to" cell can cover two lines (e.g. Poorvangam 19–22 + Poorvanyasam); everything under one Allocated to cell goes to one bhakta. It can be uploaded as is: names in Allocated to and Backup are cleared on upload (VISVAS is kept), and anything beyond column E is ignored. Columns A–E are also exactly what participants see and download. The portal shows and downloads the allocation in this same layout.

| Sheet rows | Content |
| --- | --- |
| 1–3 | Header lines: batch name (e.g. "A2322/2874 Tamil Batch (7:30PM)"), date and time (e.g. "Friday, 24th Jul 2026, 7:30PM(IST)"), satsang title — filled in by the portal each week |
| 4 | Column headings: Shlokas · From · To · Allocated to · Backup |
| 5 onward | One row per block, in chanting order, grouped by section (Opening Prayer, Pledge, Poorvangam, Dhyanam, VSN-Mahamantra, Phalashruthi, Closing Prayer) |

| Row kind | Example | How the portal treats it |
| --- | --- | --- |
| Chanting block | VSN-Mahamantra, From 13, To 16 | Given to one bhakta |
| Named part, no numbers | Poorvangam, From "Poorvanyasam" | Given to one bhakta; the text is shown as is |
| Single prayer | Opening Prayer, Pledge, Closing Prayer (one name across From–To) | Given to one bhakta, filled in its place in sheet order like any other row |
| Pre-filled row | Poorvangam 1–5 already reads "VISVAS" | Kept as is; never given to a bhakta as their block, but does get a backup |

The admin also labels each template with its slokams per bhakta (e.g. 4 or 8). The block count is simply the number of rows to fill.

**Inputs:** the template's rows in order; the pool of master-list bhaktas who chose Available (A) or Available + backup (B).

**Steps:**

1. **Select template (admin):** after voting closes, the admin picks the template for this week's allocation. The picker shows, for each template, its block count next to the number of chanters (A + B), e.g. "Template A — 4 per bhakta — 10 blocks for 12 chanters (2 on standby)" vs "Template B — 10 blocks of …". The weekly default is preselected. **The admin always chooses the template, in v1 and v2;** the system never picks one. In v2 the automatic run uses the admin's choice; if it has fewer blocks than chanters, auto-publish is held and the admin is alerted to choose another template.
2. Rows to fill = the template's chanting rows, named parts and single prayers, in sheet order. Pre-filled rows are skipped.
3. Build the chanting pool: everyone who chose Available (A) **or** Available + backup (B). Both count equally as chanters. Order the pool by master-list order with a weekly offset so the same person doesn't always get block 1.
4. Fill every row to fill — blocks, named parts and Opening Prayer, Pledge, Closing Prayer — top to bottom in sheet order, one per bhakta down the ordered pool (as in the sample sheet, the first bhakta gets Opening Prayer). Because the pool rotates weekly, the prayers rotate too.
5. **Fewer bhaktas than blocks:** after the last bhakta, start again from the top of the same ordered pool and keep assigning until every slokam is allocated (e.g. 10 blocks, 8 bhaktas → bhaktas 1 and 2 also get blocks 9 and 10). No warning; no admin action needed.
6. **More bhaktas than blocks (v1):** extra bhaktas are listed as standby with no block, and the admin is warned and prompted to go back to step 1 and pick a template with more blocks so everyone gets to chant.
7. Assign backups: after chanting is allocated, split all rows — blocks, single prayers and pre-filled rows such as VISVAS — into as many contiguous groups as there are B bhaktas, as evenly as possible. Each B bhakta becomes the backup for every block in one group, on top of their own block.
8. A backup never covers their own block. Opening Prayer and Pledge do not need separate backups: they sit in the first group with the early Poorvangam rows, and one backup covers that whole stretch. Only when there are enough B bhaktas do the groups get small enough for the prayers to have their own backups. To keep each group with one backup, the portal chooses which B bhakta takes which group so that, where possible, nobody's group contains their own block. Only if that can't be avoided is their own block covered by the next B bhakta; with only one B bhakta, that block has no backup and is flagged to the admin.
9. No B bhaktas: blocks have no backup and the admin is warned.
10. Admin reviews, edits (A9) and publishes (A10). In v2 publishing is automatic, and the admin can still edit before or after it goes live.

**Worked example:** a template with 10 rows to fill. 10 bhaktas respond: 8 Available, 2 Available + backup (Ravi gets row 3, Meena gets row 8). All 10 get one row each. Backups split the 10 rows into two groups. Ravi's own row (3) is in the first group, so Meena backs up rows 1–5 and Ravi backs up rows 6–10 — each covers a whole group and nobody covers their own row. With only one backup, that person would cover all 10 rows except their own.

**On the day / late drop-out (A12):** if the bhakta on block 8 doesn't come, the backup named for block 8 chants it in addition to their own block. The admin can record this in the portal so the published sheet shows who covered it. If two bhaktas in the same group are absent, the backup covers the first and the admin reassigns the other.

## Edge cases

| Case | Expected behaviour |
| --- | --- |
| Name typed with a different spelling ("Laxmi" vs "Lakshmi R.") | Refused with the B3 message; logged so the admin can spot near-misses |
| Name typed in different case ("lakshmi r.") or with extra spaces between words | Different case: accepted. Extra spaces between words: refused. Leading/trailing spaces are trimmed before matching |
| Someone submits using another bhakta's name | Accepted — no login by design. The later answer overwrites the earlier one; the admin sees both times in the audit log. Risk accepted |
| Duplicate name in the master list or an import | Allowed; merged into one entry. Two real people with the same name share one entry, vote and block — the admin can make the names distinct (e.g. "Lakshmi R." / "Lakshmi S.") if needed |
| Admin removes a bhakta after they responded | Response kept but excluded from allocation |
| Admin changes template after allocation generated | Draft allocation is discarded with a confirm dialog |
| Zero available bhaktas | Generate is blocked with "No available bhaktas"; v2 scheduler skips auto-publish and flags the admin |
| Row with text instead of numbers (e.g. Poorvanyasam) | Treated as one block; the text is shown in From as is |
| Allocation page opened before publish | Shows "Allocation will be shared on Wednesday morning"; previous week's allocation is not shown |
| Admin forgets to click Open/Close/Publish (v1) | Admin dashboard shows the overdue step in red; v2 removes this case |
| Time zones | The portal runs on IST (Asia/Kolkata) only. Every time is entered and shown in IST, for admin and bhaktas alike; the database may store UTC internally |

## Non-functional requirements and suggested stack

- **Scale:** design for ≤ 500 names per batch and ≤ 200 concurrent viewers.
- **Performance:** public pages load in < 2 s on 4G.
- **Privacy:** the only bhakta data stored is their name and their weekly response. No phone, email or IP addresses are kept beyond short-lived rate-limit counters.
- **Admin security:** password hashed with bcrypt/Argon2, never stored or logged in plain text; HTTPS only; login lockout (A1).
- **Abuse:** rate-limit the availability form (e.g. 10 submissions per IP per 10 minutes) and add a honeypot field.
- **Accessibility:** WCAG 2.1 AA basics; labels on all inputs.
- **Language:** English UI; slokam labels may contain Sanskrit/Devanagari, so UTF-8 throughout and PDF export embeds a Devanagari-capable font.
- **Scheduler (v2):** state is computed from the clock on every page load, plus one daily backstop job (see Chosen stack); every step is idempotent and logged.
- **Backups:** daily database backup; audit log retained 12 months.

**Chosen stack (decided Oct 26)** — picked for a solo builder using AI coding help in Visual Studio Code, at zero hosting cost:

| Layer | Choice | Why |
| --- | --- | --- |
| App | Next.js (TypeScript), one project for bhakta pages, admin pages and API | Most AI coding tools know it well; one language end to end |
| Database | PostgreSQL on Supabase (free tier), accessed through Prisma | Free, managed; the coordinator already has an account (changed from Neon on Nov 5) |
| Hosting | Vercel Hobby (free) | Push to GitHub and it deploys; HTTPS included |
| Domain | Free \*.vercel.app address to start; a custom domain can be added later | No cost or setup at launch |
| Spreadsheets | `exceljs` for template upload, master-list import and XLSX download | Reads and writes .xlsx in the app |
| PDF | A print-ready allocation page; "Download PDF" opens the browser's Save as PDF | Browsers render Devanagari correctly; PDF libraries often break conjunct letters |
| Admin password | `bcrypt` hash, stored in the database | Meets A1 |

**Scheduling without paid cron:** Vercel's free plan only allows a scheduled job once a day, and only within the hour ([Vercel docs](https://vercel.com/docs/cron-jobs/usage-and-pricing)). So the portal works out each satsang's state from the clock whenever a page loads: voting shows as open between opens\_at and closes\_at, and the allocation shows only after publish\_at. The first request after voting closes generates the allocation (v2). One daily cron job is a backstop that creates next week's satsang and generates any allocation still missing. This gives exact Monday/Tuesday/Wednesday timings on the free plan.

## Rollout plan

1. **Build & test (v1):** admin seeds the master list and one template; run a dummy week with 3–5 volunteers.
2. **Pilot (v1):** one real satsang, with the WhatsApp poll kept as a fallback that week.
3. **Go-live (v1):** share the portal link in the WhatsApp group; stop posting polls once the pilot hits the response-rate and on-time targets.
4. **v2 automation:** turn on auto-mode so open, close, generate and publish run on schedule; admin only handles exceptions.

**Rollback:** admin exports the master list and last allocation (XLSX) and goes back to the WhatsApp poll. No data is locked in.
